**1. Introduction**

For over 20 years software engineering researchers
have suggested numerous techniques for estimating
development effort, based mainly on late project
measures, such as lines of code, function points, number
of HTML pages etc. However, for the successful
management of software projects, estimates are necessary
throughout the whole development life cycle [1]. For
example, preliminary estimates are fundamental when
bidding for a contract or when determining a project’s
feasibility in terms of cost-benefit analysis. Unfortunately,
these are the most difficult to measure, and are often
inaccurate as there is little information about projects and
product at an early stage [2].
For three years we have focused on the proposition and
comparison of effort prediction models for Web
hypermedia applications based on application measures
collected at the end of the development life cycle


(implementation phase) [3-7]. However for this work, we
focus on the harvesting of size measures at different points
in the development life cycle, to estimate development
effort, and their comparison based on several prediction
accuracy indicators. Our aim is to investigate how
different these predictors are and if there are any
statistically significant differences between them.
The category of applications focus for this
investigation is denominated Web hypermedia, as
opposed to Web software [8]. The former represents nonconventional applications, characterised by the structuring
of information using nodes (chunks of information), links
(relations between nodes), anchors, access structures (for
navigation) and the delivery of this structure over the
Web. The latter represents any conventional software
application that depends on the Web, or uses the Web's
infrastructure, for execution. Typical Web software
applications include legacy information systems such as
databases, booking systems, knowledge bases etc. Many
e-commerce applications also fall into the latter category.
Web hypermedia applications have great potential in
areas such as software engineering [9], literature [10],
education [11], and training [12], to mention but a few.
Readers interested in effort estimation models for Web

software applications are referred to [13,14].
The objective of this paper is twofold. First, we
describe the application of case-based reasoning for
estimating Web hypermedia development effort using
measures collected at different stages in the development
cycle. Second, we compare the prediction accuracy of
those measures, obtained using different case-based
reasoning (CBR) configurations.
Those objectives are reflected in the following research
questions:
1) Will application measures generate significantly
better prediction accuracy than requirements &
design measures?

These issues were investigated using data gathered
through a case study where sets of suggested metrics for

from the function bang and data bang measures [1],

The process model we employed was an adaptation of
the waterfall model (see figure 1), where iteration was
added to reflect the type of applications developed. We
collected measures at three stages: prior to the case study,
at the end of phase I and at the end of Phase II.

**Figure 1 - Process Model used in the case study**

Functional requirements were measured using UML
use case diagrams [17]. The Data design was in effect the
Entity-Relationship Diagram [18]. The Navigation Design
helped identify the main structure of a Web site, in terms
or pages (nodes) and links (anchors). We did not use any
existing hypermedia models, such as OOHDM [19],
RMM [20], HDM [21] as we wanted subjects to use
familiar techniques. Therefore the only new concept
introduced was the navigation design. In addition, the
choice for using three separate diagrams during Phase I is
justified on the grounds that hypermedia applications are
centred on three pillars: data, functionality and navigation,
each giving a different perspective on the overall
application being developed.
In this paper we chose CBR as a prediction technique
for the following reasons:

- An early study comparing CBR to other prediction
techniques [4], showed that CBR presented the best
prediction accuracy when using a of Web hypermedia
dataset.



- A second study, using a different Web hypermedia
dataset, also showed good prediction accuracy using
CBR [7].

- CBR is an intuitive method with evidence that experts
apply analogical reasoning when making estimates

[22].

- CBR can be used on qualitative and quantitative data,
reflecting closer types of datasets found in real life.

- Investigation of our dataset revealed no linear
relationships between application measures and
development effort, even when using General Linear
Models with different distributions, such as Poisson or
Gamma, or after transforming the data.

The rationale for CBR is to characterise the project, for
which the estimate is to be made, relative to a number of
attributes (e.g. application complexity, link complexity
etc). This description is then used to find other similar
finished projects, and an estimate for the new project is
made based on the known effort values for those finished

projects [23].
This paper is organised as follows: Section 2 presents
in more depth the technique of case-based reasoning.
Section 3 describes the case study used to collect the
measures employed in this investigation. Section 4
describes the empirical results for both early-collected and
late-collected measures. Finally, Section 5 concludes with
an analysis of the strengths and weaknesses of using CBR
and suggestions on future work.

**2. Case-based Reasoning**

Case-based Reasoning involves [23]:
� Characterising the project for which an estimate is
required, i.e., identifying project attributes (application
size, link complexity etc) which can influence effort.
� Use of this characterisation data as a basis for finding
similar (analogous) completed projects, for which
effort is known.

� Use of these effort values, with possibly adjustment, to
generate a predicted value of effort.

When using CBR there are a number of parameters to
decide upon [24,25]:

- Similarity measure

- Scaling

- Number of analogies

- Analogy adaptation

- Feature Subset Selection

Each parameter can be divided into more detail, for
incorporation into a CBR tool, allowing for several CBR
configurations.

**2. 1 Similarity Measure**

Similarity Measure measures the level of similarity
between cases. To our knowledge, the similarity measure
most frequently used in Software engineering and Web
engineering literature is the unweighted Euclidean
distance. In the context of this investigation we have used
two measures of similarity, namely the unweighted
Euclidean distance and the weighted Euclidean distance,
each of which are detailed below:

All formulas presented in this sub-section assume that *x*
and *y* represent size attributes for Web hypermedia
applications, e.g., *x* might be page-count and *y* pagecomplexity. The pair ( *x* *i*, *y* *i* ) represents instances of *x* and *y*
for project *i* .

**Unweighted Euclidean distance:** The Euclidean distance
*d* between the points (x 0,y 0 ) and (x 1,y 1 ) is given by:


*d* = ( *x* 0 − *x* 1 ) 2 + ( *y* 0 − *y* 1 ) 2 **(1)**


**Weighted Euclidean distance:** It is common in CBR for
the features vectors to be weighted to reflect the relative
importance of each feature. The weighted Euclidean
distance *d* between the points *(x* *0* *,y* *0* *)* and *(x* *1* *,y* *1* *)* is given
by:


*d* = *w* *x* ( *x* 0 − *x* 1 ) 2 + *w* *y* ( *y* 0 − *y* 1 ) 2 **(2)**


where *w* *x* and *w* *y* are the weights of *x* and *y* respectively.

**2.2 Scaling or Standardisation**

Standardisation represents the transformation of
attribute values according to a defined rule such that all
attributes are measured using the same unit. One possible
solution is to assign the value *zero* to the minimum
observed value and *one* to the maximum observed value

[24]. This was the strategy chosen for the analysis carried
out using CBR-Works (see Section 5).

**2.3 Number of Analogies**

The number of analogies refers to the number of most
similar cases that will be used to generate the estimation.
For Angelis and Stamelos [26], when small sets of data
are used it is reasonable to consider only a small number
of analogies. In this study we have used 1, 2 and 3
analogies, similarly to [4,7,26-30].

**2.4 Analogy Adaptation**
Once the most similar case(s) has/have been selected
the next step is to decide how to generate the estimation.


Choices of analogy adaptation techniques presented in the
Software engineering literature vary from the nearest
neighbour [27,29], the mean of the closest analogies [31],
the median [26], inverse distance weighted mean and
inverse rank weighted mean [24], to illustrate just a few.
In the Web engineering literature, the adaptation used to
date is the mean of the closest analogies [4,7]. We opted
for the mean, median and the inverse rank weighted mean.

*Mean:* Represents the average of k analogies, when k>1.
*Inverse rank weighted mean:* Allows higher ranked
analogies to have more influence than lower ones. For
example, using 3 analogies, the closest analogy (CA)
would have a weight = 3, the second closest (SC) a weight
= 2 and the last one (LA) a weight =1. The estimation
would then be calculated as (3*CA + 2*SC + LA)/6.
*Median:* Represents the median of k analogies, when k>2.

**2.5 Feature Subset Selection**

Feature subset selection involves determining the
optimum subset of features that gives the most accurate
estimation. This can be accomplished by applying a brute
force algorithm against the feature subset search domain

[24]. We did not use this option, as the CBR Tool
employed in this evaluation does not offer such
functionality.
All estimations presented in this paper were generated
using CBR-Works [32, 33].

**3. The Case Study**

**3.1 Dataset**

The dataset (DS, 25 applications) was obtained using a
case study (CS) consisting of the development, by pairs of
subjects, of Web hypermedia applications structured using
an adaptation of the Unified Modelling Language [17],
with a minimum of 25 pages. Each Web hypermedia
application provided 42 items of data, from which we
identified 12 attributes, shown in Tables 1 and 2, to
characterise a Web hypermedia application and its
development process. The dataset is presented in
Appendix A. Subjects were Computer Science Honours
and postgraduate students, attending a Hypermedia and
Multimedia Systems course at the University of Auckland
during the first semester of 2001.
Tables 1 and 2 show the attributes that form a basis of

our data analysis. Total effort is our dependent/response
variable; remaining attributes our independent/predictor
variables. All attributes were measured on a ratio scale.

The criteria used to select the attributes was [15]: i)
practical relevance for Web hypermedia developers; ii)

Three questionnaires were used to collect data. The
first [1] asked subjects to rate their Web hypermedia
implementation experience using five scales, from no
experience (zero) to very good experience (four). The
second questionnaire [2] was used to measure the effort to
prepare the Use case diagram, Entity-relationship diagram
and Navigation diagram. Finally, the third questionnaire [3]
was used to measure characteristics of the Web

hypermedia applications developed (suggested metrics),
their implementation experience and the effort involved in
implementing and testing those applications. On all
questionnaires, we describe in depth each scale type, to
avoid misunderstanding. Members of the research group
checked both questionnaires for ambiguous questions,
unusual tasks, and number of questions and definitions in
the Appendix.


To reduce learning effects, subjects were given a
coursework prior to developing the Web hypermedia
applications, consisting of creating a simple Web
hypermedia application and loading the application onto a
Web server. In addition, in order to measure possible
factors that could influence the validity of the results, we
also asked subjects about the main structure (backbone) of
their applications [4], their authoring experience before and
after developing the applications, and the type of tool used
to author/design the Web pages [5] .
Finally, subjects received training on the design of
Navigation Diagrams (approximately 120 minutes).

**4. Comparing Predictors**

**4.1 Evaluation Criteria**

The most common approaches to assessing the
accuracy of prediction models are:

- The Mean Magnitude of Relative Error **(MMRE)** [23]

- The Median Magnitude of Relative Error **(MdMRE)**

[34]

- The Prediction at level n **(Pred(n))** [31]

- Boxplots of residuals [35, 36]

We have used all four approaches to assess the
accuracy of the different Predictors and CBR
configurations presented in this paper.
The statistical significance of all the results was tested
using the T-test and Wilcoxon Rank Sum Test (α = 0.05),
whenever we had to compare paired variables, and a Ttest and the Mann-Whitney U test (α = 0.05) otherwise.
All calculations were done using SPSS for Windows
release 10.1.0.

users need to configure the CBR tool according to four
different parameters (similarity measure, scaling, number
of analogies and analogy adaptation).

1) Will application measures generate significantly better
prediction accuracy than requirements & design
measures?

2) Which of the CBR configurations, for each class of
