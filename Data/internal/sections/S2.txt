**Abstract**

*In this paper we explore the variation of the cost of*
*writing code when object- oriented framework based*
*development of web applications is encountered for the*
*first time. Managers need such information to justify their*
*investments in innovative development strategies. Size*
*measurements are essential in this task and a number of*
*metrics, namely Lines of Code, classical Function Points*
*and Object-Oriented Function Points, are employed. It is*
*argued that lines of code and object-oriented function*
*points are more suitable in this case. Data analysis*
*reveals that learning influences mainly the cost of writing*
*new code, consisting of continuous calls to components*
*provided by the framework. We also explore the*
*applicability of an already proposed effort prediction*
*model that is based on different reuse types. A cost*
*estimation model is the by-product of this study, providing*
*a helpful tool for managing the first projects in which the*
*framework is employed* .

**1.** **Introduction**

Object Oriented frameworks provide an important
enabling technology for reusing the architecture and
functionality of software components. Despite the heavy
reuse involved in framework–based development,
application design based on frameworks continues to be a
difficult task. The designer must understand the complex
class hierarchies and objects embodied in the framework
in order to use the framework effectively. This is the
reason for the relatively low productivity that is reported
for the first applications developed using the framework.
Therefore managers need tools to justify their investment


in framework technology. They need ways to monitor
productivity growth and models to estimate return on
investment for framework adoption.
In the experiment described in a companion paper [1],
a number of Web based applications were developed
using an object oriented framework. This framework
supports the development of multimedia services on a
digital network using CORBA infrastructure and
integrating COTS (Component Off-The-Shelf) products
such as CU-See-Me. The framework is composed of a
service platform, to abstract common functions from a
network, and components to abstract control services. The
development of applications consists of the verbatim
reuse of the framework plus the development of new
code, in Java, which implements calls to the components
provided by the framework.
As reported in [1], significant reuse level and high
productivity characterizes framework-based applications’
development. Another important concept related to the
framework based software development is the impact of
the learning effect, since the user must fully understand
the abstract design of the underlying framework, as well
as the object collaboration rules or contracts. In [2] it is
stated that there is a linear relationship between
productivity and *Reuse* *Level* ( *Reuse* *Rate* ). Whether this
relationship is linear or not, it is expected that higher
Reuse Level results in higher productivity. This does not
apply in the first applications developed using the
framework due to the learning factor.
Our aim was to construct a cost estimation model that
would take into account the learning factor, in order to
calculate the relative cost of writing new code that uses
the framework, when the framework is used for the first
time. As stated in [3] frameworks have a steep learning
curve. However this is not proved using any empirical
data. Using the empirical data from the development of
five applications with the framework we tried to construct

**2.** **Measuring the framework-based**
**applications**

**2.1.** **Measuring the size**

The first approach used in order to measure the size of
the applications developed using the framework was
Function Point Analysis (FPA). Function Point counting
rules were initially introduced by Allan Albrecht, IBM, in
1979 ([6]). These rules have been reviewed by the
International Function Point User Group. The focus of the
rules is to measure the functional size of software from a
user point of view. Function Points are often used in cost
estimation tools such as algorithmic cost models.
The first problem in applying the IFPUG rules ([7],

[8]) was the nature of these applications. As stated earlier
the experiment involved Web-based object oriented
applications and therefore an adaptation of these rules was
necessary.  A tutorial ([9]) was used in order to adapt
IFPUG Counting rules to this specific kind of
applications. The second problem related to Function
Points is that this measure does not enable the distinction
between functionality provided by the framework and by
the code developed for the specific application. This leads
to the conclusion that Function Points can not be used in
order to measure the Reuse Level *,* and as a consequence
this metric cannot be used to build an estimation model
that incorporates reuse.
The second metric that was used was the Object
Oriented Function Points (OOFPs). OOFPs were
introduced in [10] as a method used for estimating the
size and consequently the effort and duration of object
oriented software development projects. In Function
Points the central concept are *logical files* and


*transactions* . In OOFPs the central concept are the classes
and their methods. There is a mapping between classes
and files and methods and transactions. In FPA, logical
files (LF) are divided into *internal logical files* *(ILFs)* and
*external interface files (EIFs)* . This division is made by
identifying the application boundary. In OOFPs classes
are divided into external classes and internal classes.
External classes refer to non–system components, such as
other applications, external services and reused library
classes. Classes within the application boundary
correspond to ILFs, while classes outside the application
boundary correspond to EIFs.
Transactions in FPA are classified as *inputs, outputs*
and *inquiries* . In OOFPs class methods are used instead of
transactions. Class methods are treated as *Service*
*Requests* (SR) whether they belong to external or to
internal classes.
The complexity of each class is calculated by counting
single attributes of each class as *Data Element Types*
(DETs) and complex attributes, (i.e. attributes which type
is a class), as Record Element Types (RETs). Then
complexity look-up tables for *logical files* introduced by
IFPUG rules are used in order to count the OOFPs.
The complexity of each Service Request is calculated
by counting the arguments of each method. *Simple*
*arguments* are counted as DETs, while *complex*
*arguments*, such as objects, are counted as File Types
Referenced (FTRs). When the DETs and FTRs of a
method have been counted, the IFPUG Counting Practices
Manual table for external inputs is used in order to
classify the methods as having low, average or high
complexity.
OOFPs in contrast with Function Points enable the
counting of Reuse Level because a clear distinction can be
made between classes that were developed and classes
that were reused, and also Service Requests provided by
new developed classes and Service Requests provided by
reused classes. In contrast with LOCs, OOFPs enable the
measurement of the size of an application at the OO
design phase, while LOCs can be used only at the end of
the implementation phase. Even if the exact number of
classes and methods is not known at the early design
phase, an estimation of the size of the software in OOFPs
can be obtained counting the number of classes and
assigning a low complexity to each of them. The fact that
OOFPs can be counted early enough in the development
cycle implies that this metric is more suitable in order to
build a cost estimation model.

The third metric in order to measure the size of the
software is Lines of Code which is the number of physical
lines of code delivered in each application. For a specific
application the size expressed in LOCs includes the Lines
of Code of the framework which is verbatim reused.

**5.** **Conclusions**

In this paper we have measured the functional size and


the code size of the software produced during an
experiment involving the development of web-based
applications using an object-oriented framework. Three
different metrics have been used for this purpose, Lines of
Code, classical Function Points and Object-Oriented
Function Points.
It is important to fully understand the productivity
implications in this type of software development.
Software managers need to keep under control
productivity variation in the first applications of the
framework, since, initially, it is reasonable to expect
lower than normal productivity.
Although function point analysis is suitable for
determining the amount of functionality provided by a
software product, function points can not reflect the extent
to which code reuse has been applied in development.
Therefore, they are inappropriate for productivity
estimations in this type of software development. On the
contrary, lines of code and object-oriented function points
are capable of measuring reuse.
Based on size measurements with these metrics and
taking into account the different types of reuse we have
found that the cost of writing new code (consisting mainly
of calls to components provided by the framework) is
reduced, following a traditional learning curve.
Based on the above we have built a simple cost
estimation model that may be used by managers that are
asked to invest in this technology and direct such software
development projects. This model helps in predicting and
tracking development costs during the first exploratory
projects. The parameters of the models are specific to the
context of the experiment, but we believe that the
methodology followed is applicable in other development
environments as well.
Finally, we have found that lines of code and OOFPs
are equally suitable for measurements in this field. We
prefer the latter because OOFPs are available earlier in the
software development cycle.
