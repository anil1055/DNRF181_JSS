**1. Introduction**

Recently, growth of the Web as a delivery environment
has given rise to a new research field - Web engineering,
the application of engineering principles to develop
quality Web applications [1].
The Web is used as the delivery platform for two types
of applications: Web hypermedia applications and Web
software applications [2]. A Web hypermedia application
is a non-conventional application characterised by the
authoring of information using nodes (chunks of
information), links (relations between nodes), anchors,
access structures (for navigation) and its delivery over the
Web. Technologies commonly used for developing such
applications are HTML, JavaScript and multimedia. In
addition, typical developers are writers, artists and
organisations who wish to publish information on the
Web and/or CD-ROM without the need to use
programming languages such as Java.
Conversely, a Web software application represents
conventional software applications that depend on the
Web or use the Web's infrastructure for execution.
Typical applications include legacy information systems
such as databases, booking systems, knowledge bases etc.
Many e-commerce applications fall into this category.
Typically they employ technology such as Components
off-the-shelf, components such as DCOM, OLE, ActiveX,
XML, PHP, dynamic HTML, databases, and development
solutions such as J2EE. Typical developers are young
programmers fresh from a Computer Science or Software
Engineering degree, managed by more senior staff.

We use Web application to refer to both Web
hypermedia and software applications.
A variety of technological solutions are available for
Web developers to facilitate the delivery of quality Web
applications and bring them quickly to market, with
typical durations ranging from 3 to 6 months [3].
However, there are no standardised development
techniques or large datasets of historical data on Web
development projects.
For Web development, cost can be very challenging to
estimate because:

- There is no standard way of sizing Web applications.
Each can be created using diverse technologies such
as varieties of Java (Java, servlets, Enterprise java
Beans, applets, and Java Server Pages), HTML,
JavaScript, XML, XSL, and so on.

- Web project’s primary goal is to bring quality
applications to market as quickly as possible, varying
from a few weeks [1] to 6 months [4].

- People involved in Web development are represented
by less experienced programmers, users as
developers, graphic designers and new hires straight
from university [4].

- Typical project team size is small, between 3 to 7
members [4].

- Processes employed are in general heuristic, although
some organisations are starting to look into the use of
agile methods [5].

Over the last seven years hypermedia size measures
have been adapted and new size measures were proposed
for Web applications [3,6-14].
Size is considered a primary input to software cost
models, and to be of use, must be estimated at the start of
the development process.
To date few papers have proposed Web size measures

[13,14,3,7-11] aimed at Web costimation. [13,14,3,10]
have used industrial datasets of Web projects to justify
their size measures and to generate corresponding cost
models, each collecting their data from just one Web
company, which may affect the external validity of their
results. [9] proposes size measures for static and dynamic
Web applications and [8] proposes size measures for Web
hypermedia applications. However the datasets employed
in these studies are based on Web applications developed
by students, which may also affect the external validity of
their results.
Another aspect of importance for the generation of
costimation models is the availability of datasets of past
finished projects. These datasets are used to generate
models then applied to estimate costs for new projects.
Although prediction can be generated using different
models (algorithmic, machine learning-based etc) it seems
that for most, if not all, the number of finished projects


available in a dataset is directly related to the model’s
prediction accuracy.
It is believed that company-specific datasets provide
better basis for accurate estimates. However, the time
required to accumulate enough data on past projects from
a single company may be prohibitive. In addition, by the
time the dataset is large, technologies used by the
company may have changed, and older projects may no
longer be representative of current practices [15]. Multicompany datasets (datasets containing data from several
companies) is an approach to populate a large dataset of
projects for prediction purposes. However, care is
necessary as data needs to be collected in a consistent
manner and differences in processes and practices, trends
may differ considerably across companies [15].
Several studies in Software engineering have compared
the prediction accuracy of multi-company vs. companyspecific datasets [15-19] however a comparison using
Web datasets has not been done.
As a result, this paper’s contribution is twofold: First,
it presents a survey where early Web size measures for
early costimation were identified using data collected
from 133 Web companies worldwide. These companies
use Web forms to give quotes on Web development
projects, based on early size measures. The survey results
were used as input for the gathering of Web project data
as part of a research project called the “Tukutuku [2]

Benchmarking Project” (Section 2.4). Second, it
compares the feasibility of using multi-company datasets
to build Web costimation models compared to companyspecific data using datasets obtained from the Tukutuku
database.
The remainder of the paper is organised as follows:
Section 2 briefly describes the survey carried out, its
results and how the Web project datasets were obtained.
Section 3 describes the comparison of a multi-company
Web dataset to a company-specific Web company dataset.
Conclusions and comments on future work are given in
Section 4.

**2.2 Results**

The data collected from 133 on-line quotes was
organised into 5 categories:
1. Web application static measures
2. Web application dynamic measures
3. Web Project measures
4. Web company measures
5. Web interface design measures

In the scope of this investigation size is represented
using three attributes [21]: length, functionality and
complexity. Length measures the physical size of a Web
application; functionality measures the functions supplied
by the application to the user; complexity of an application
is measured by its structural complexity [21], where the
structure of an application is represented by how Web
pages are interconnected by links. Structures can be of
three types: linear, hierarchical and network [22].

**Answering the survey research questions:**

- *What are the size measures used as early cost*
*estimators by Web companies?*
Size measures identified in the survey are presented in
Table 1, under **Web application static measures** and
**Web application dynamic measures** . Observe that no
complexity measures have been identified. Those that
have been ranked highest are possibly the most important,
given that they were suggested by the greatest number of
Web companies. For static measures, Web companies
require from the beginning, how much information (text,
photos, images) ready to use is provided by customers,
how much information needs to be digitized or needs to
be created from scratch. Number of pages was also
important information. We believe this to be the case as
most Web companies use number of pages as one of the
core components for Web applications (e.g., 5 pages with
text only or 5 pages with text, images etc). Regarding
dynamic measures, Web companies listed features and
functionality, rather than using a more sophisticated
mechanism to measure functionality. This is probably due
to the difficulty in identifying well-defined functional
components early on in the development.

- *Which measures are used the most?*
According to the survey, the two measures used the
most are *total number of Web pages* and *which*
*features/functionality* . Together they represent 70% and
66% respectively of those Web companies that
participated in the survey. This suggests that they are the
two strongest effort predictors obtained from the survey,
despite the need for empirical evidence to support this
claim. It is interesting that *total number of Web pages*
represents a length measure, characteristic of Web
hypermedia applications and *which features/functionality*


represents more closely an abstract measure of
functionality, characteristic of Web software applications.
We believe this is an attractive result as it seems to
suggest a balance between static and dynamic
characteristics which may be present in Web applications.
In addition, *total number of Web pages* has also been the
measure chosen by most literature in Web costimation

[20].

- *Which* *measures* *are* *characteristic* *of* *Web*
*hypermedia applications?*
The category **Web application static measures**
characterise closely Web hypermedia applications.

- *Which measures are characteristic of Web software*
*applications?*
The category **Web application dynamic measures**
characterise closely Web software applications.

**2.3 Moving Towards a Repository of Web**
**Projects**

Once the ranking described in the previous sub-section
was completed, the next stage was to contact an
experienced Web company to confirm/deny, based on the
ranking provided, those measures identified as most
important for early costimation. Based on this company’s
feedback, we prepared Web forms to be used to gather
data on Web projects worldwide. This data gathering
initiative is called the Tukutuku benchmarking project
(Section 2.4).
The Web company contacted is based in Rio de
Janeiro, Brazil. Five people work in Web design and
development within the company. Three of those are
company directors, also managing Web projects and
preparing quotes for customers. This company has a
portfolio of more than 50 Web applications and has been
established for 10 years. They use a documented process
and depending on the type of project, one out of two types
of process models are used: incremental prototyping or
waterfall.
One of the directors was contacted by one of the
authors and helped validate the measures identified in the
survey. This director has worked in software development
for 18 years and is experienced in management of large
projects, conventional or Web-based.
For Web application static measures, agreement was
reached for most (from number 1 to 18, see Table 1),
examining those which could actually be estimated early
on in the Web development life cycle. More measures
were added to the list, and some were re-arranged (see
Table 3, Section3).
For Web application dynamic measures, more
features/functionality were added to the list and suggested

**3.2 Threats to Validity**

Predictor variables were based on the results of our
survey, which in turn were based on data from Web
costimation forms gathered worldwide. Consequently we
believe we have used predictors that are meaningful and
realistic measures for Web companies. However we have
not supplied Web companies with automatic measurement
tools that could be used to gather data on their Web
applications. We relied on their own mechanisms to do
so, meaning that we cannot guarantee 100% accuracy.
Regarding our response variable, in order to have a better
idea of how reliable the effort data entered was, we also
asked how the effort data has been collected (Table 6).
Two companies had collected effort differently
depending on the project ( 1 and (3 or 4)).
More than half of the projects had effort which has
been recorded for each day or week, so we believe these
values have not been guessed.

*Case-based Reasoning (CBR)*
The rationale for CBR is the use of historical
information from completed projects with known effort. It
involves [26]:
�� Characterising a new active project *p,* for which an
estimate is required, with attributes (features)
common to those completed project stored in the case
base. In our context most features represent size
measures which have a bearing on effort. Feature
values are normally standardized (between 0 and 1)
such that they have the same degree of influence on
the results.
�� Use of this characterisation as a basis for finding
similar (analogous) completed projects, for which
effort is known. This process can be achieved by
measuring the “distance” between two projects, based
on the values for the *k* features for these projects.
�� Generation of a predicted value of effort for project *p*
based on the effort for those completed projects that
are similar to *p* . The number of similar projects
normally depends on the size of the dataset. For small
datasets typical values are 1, 2 and 3 closest
neighbours (analogies). The calculation of estimated
effort is often obtained by using the same effort value
of the closest neighbour, or the mean of effort values
(2 or more analogies). In Software engineering and
Web engineering a common choice is the nearest
neighbour or the mean for 2 and 3 analogies.

When using CBR there are a number of parameters to
decide upon [24]:

- Feature Subset Selection - optimum subset of features
that give the most accurate estimation.

- Similarity Measure - the level of similarity between

cases.

- Scaling - transformation of attribute values according
to a defined rule such that all attributes have the same
degree of influence and the method is immune to the
choice of units [26].

- Number of analogies - the number of most similar
cases that will be used to generate the estimation.

- Analogy Adaptation - how to generate the estimation
for the “new” project *p* .


All the results for CBR were obtained using CBRWorks [27], a commercially available CBR tool.
As CBR-Works does not offer the Feature Subset
Selection option, we used the Weighted Euclidean
distance as the similarity measure. Weights attributed to
variables were obtained by measuring the linear
association between the predictor and response variables
using a two-tailed Spearman’s rho test, a non-parametric
test as most variables are not normally distributed. All
values were scaled between 0 and 1. Regarding the
number of closest analogies, although the nearest
neighbour showed very good prediction accuracy for
another Web projects dataset [28] we decided to use 1, 2
and 3 analogies.

*Stepwise Regression (SWR)*
Stepwise regression [29] builds a prediction model by
adding to the model, at each stage, the variable with the
highest partial correlation to the response variable, taking
into account all variables currently in the model. Its aim is
to find the set of predictors that maximise *F* . *F* assesses
whether the regressors, taken together, are significantly
associated with the response variable. The criteria used to
add a variable is whether it increases the *F* value for the
regression by some specified amount *k* . When a variable
reduces *F*, also by some specified amount *w,* it is removed
from the model.
Stepwise regression has been frequently used as a
benchmark [30,23,24,9] and is regarded by some as a
good prediction technique [31].
Linear models revealed heteroscedasticity so we had to
investigate a plausible functional form to fit our data. The
exponential functional form was the most reasonable. We
have also estimated effort for both datasets by applying
the stepwise ANOVA procedure [32]. However, as
stepwise regression presented slightly better results, we
only provide the results obtained using stepwise
regression.
All statistical analyses presented in the paper, were
conducted using the statistical software SPSS v.10.01

[33].

**3.4 Evaluation Criteria**

Results are compared using the Mean Magnitude of
Relative Error [30], Prediction at level n (Pred(n)) [34]
and boxplots of absolute residuals [35] as measures of
prediction accuracy. MMRE was chosen for two reasons:
Firstly, MMRE is the de facto standard evaluation
criterion to assess the accuracy of software prediction
models [36]; Secondly, recent empirical investigation did
not find evidence to discourage the use of MRE and
MMRE [37].
Pred(n) is used because it is also an indicator which is
commonly used to assess prediction accuracy.
Suggestions have been made [38] that n should be set at

**3.5 Cross-validation**

To generate the estimations for each dataset, for both
CBR and stepwise regression, we used a twenty-fold
cross-validation approach [39], as according to recent
studies, less than twenty training/validation sets may lead
to untrustworthy results [39].
Cross-validation involves dividing the whole dataset
into multiple train and validation sets, calculating the
accuracy for each validation set, and aggregating the
accuracy across all validation sets. A twenty-fold crossvalidation yields twenty different training-validation set
combinations. Each validation set is randomly generated
from the original dataset, and we use the remaining
projects as the training set. There is no standard to what is
the best size for training sets. However, as it seems that
larger training sets reduce prediction errors (measured as
absolute residuals) [24] we decided to use a split where
there were more projects in the training set than in the
validation set, similarly to [15]. We used a 66% split (For
the multi-company dataset, 16 observations in the train set
and 8 in validation set; for the company-specific dataset, 8
observations in the train set and 4 in the validation set).
We therefore had in total twenty different combinations
for each technique employed.

**4. Conclusions and Future Work**

In this study we investigated two issues related to Web
costimation, which were:
1) What early Web size measures are used by industry
for Web costimation.
2) The feasibility of using multi-company datasets to
build Web costimation models as compared to
company-specific data.

Early Web size measures for Web costimation were
identified using a survey where data from 133 Web
companies worldwide were collected. These companies
use Web forms to give quotes on Web development
projects, based on gathered early size measures. Two size
measures stood out, ***total number of Web pages*** and *which*
***features/functionality*** . The first is a typical length size
measure and the second is an abstract measure of
functionality. The survey results were used as input for the
gathering of Web project data, which is as part of a
research project called the Tukutuku Benchmarking
Project.
Regarding the use of Multi-company datasets vs.
Company-specific datasets our results suggest that best
predictions were obtained for company-specific datasets,
corroborating previous work using non Web-based project
