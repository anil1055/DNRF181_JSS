**2. Dataset Description**

In this section the Tukutuku database [23] is
described. This database is part of the Tukutuku
project, which aims to gather data from completed
Web projects, to develop Web cost estimation models
and to benchmark productivity across and within Web
Companies [23]. This database includes information on
Web hypermedia systems and Web applications [6].
The former are characterized by the authoring of
information using nodes (chunks of information), links
(relations between nodes), anchors, access structures
(for navigation) and its delivery over the Web. In
addition, typical developers are writers, artists and
organizations that wish to publish information on the
Web and/or CD-ROMs without the need to use
programming languages such as Java. Conversely, the
latter represents applications that depend on the Web
or use the Web's infrastructure for execution and are
characterized by functionality affecting the state of the
underlying business logic. Web applications usually
include tools suited to handle persistent data, e.g. local
file system, (remote) databases, or Web Services.
Typical developers are young programmers fresh from
a Computer Science or Software Engineering degree,
managed by more senior staff.
The Tukutuku database has data on 195 projects,
where:

−
Projects came mostly from 10 different countries,
mainly New Zealand (47%), Italy (17%), Spain
(16%), Brazil (10%), United States (4%), England
(2%), and Canada (2%).

−
Project types are new developments (65.6%) or
enhancement projects (34.4%).

−
About dynamic technologies, PHP is used in 42.6%
of the projects, ASP (VBScript or .Net) in 13.8%,
Perl in 11.8%, J2EE in 9.2%, while 9.2% of the
projects used other solutions. The remaining
projects used only HTML and/or Javascript.
Each Web project in the database was characterized by
process and product variables [23]. Summary statistics
for the numerical variables from the Tukutuku database
are given in Table 1, while Table 2 summarizes the
number and percentages of projects for the categorical
variables. Note that those variables are binary, and for
our analysis their values have been coded by positive
integers, namely 1 (for “new” and “no”) and 2 (for
“enhancement” and “yes”).

**3. Support Vector Regression**

In this section, we present Support Vector
Regression (SVR) and describe the settings employed
in our case study. SVR is a regression technique based
on Support Vector Machines, a very effective and
mathematically well founded machine learning
approach [39],[41].
The large number of applications of support vector
approaches to machine learning tasks are due not only
to their performance, but also to the fact that they can
be easily paired with “kernel functions”, which, as
discussed below, allow an actual nonlinear
transformation of the input data space. For the problem
at hand, we consider the application of the support
vector approach to function estimation, obtaining a
Support Vector Regression (SVR). A good
introduction to SVR’s mathematical background, some
extensions, implementations and a list of references are
given in [37]. Pointers to papers about SVR’s history
can also be found in the References Section of the cited

tutorial.

**Figure 1 The soft margin loss setting for a**
**linear SVM [37]**

In effort estimation, both input features and effort
estimate, are real numbers. In the version of ε-SVR
where no kernel is introduced, we aim at finding the
line which best approximates the training data, but we
allow an error no greater than ε, thus focusing on
training points which are further than ε from the
candidate line. Amongst all possible solutions, the
flattest one is chosen.
In some cases, it is not possible to find a function
satisfying all constraints, and the introduction of slack
variables becomes necessary in order to relax the ε
precision constraint for some of the points. A constant
C is introduced to represent a tradeoff between the
flatness of the function and the amount of error
introduced by slack variables. Efficiency reasons
suggest the solution of the optimization problem in the
primary or dual space depending on whether the
number of dimensions is smaller or larger than the

number of training examples. The solution of the dual
problem, with the introduction of Lagrange multipliers,
shows how the solution can be expressed as a linear
combination of some of the training examples, namely
the support vectors. The complexity of the function
representation only depends on their number.
Moreover, the introduction of Lagrange multipliers and
dual space solution makes the use of kernel functions

[36] particularly smooth. Kernels are very effective to
solve the problem using a non-linear case. Indeed,
using a kernel corresponds to a dot product in the
feature space, where we apply the linear version of
support vector machines. The literature proposes a
large choice of such functions; some of them are of
general application, while others are specific to
particular domains. All induce different deformations
of the input data space. For our case study, we applied
four kernels, namely linear, polynomial, Gaussian and
sigmoid, using the SVM-light software [18] [1] .
The actual application of SVR requires the choice
of values for two sets of parameters: one regarding the
support vector algorithm, including the choice of ε and
C, as discussed above, and a second set regarding the
specific kernel adopted. In our experiments, we have
tested various parameter settings. The results of a set of
preliminary experiments performed basically
confirmed the discussion reported in [31], where the
best predictions were obtained with small values of ε
(10-4).
Another key point of the application of SVR relates
to the features’ normalization. Large differences in the
features’ values can have the unwanted effect of giving
greater importance to some of the examples with
respect to the others. This is especially true for the data
we considered, since, as reported in Table 1, the
feature values corresponding to the different projects
are very different in the Tukutuku database (e.g.:
nLang is in a range 1..8, while TotWP is 1..2000]). To
avoid such a risk, we considered two possible
strategies: normalization and logarithmic
preprocessing. The former consists in separately
considering each feature vector and dividing each of its
elements by the norm of the vector, in order to force all
vectors to have norm equal to one. Logarithmic
preprocessing is usually adopted to reduce differences
between values: herein we applied it to all the features’
values. Crucially, both operations only require the
knowledge of a single feature vector and can be
applied also to new items for which effort needs to be
evaluated.
Furthermore, let us recall that among the different
solutions, SVR chooses the one corresponding to the

flattest. This is not necessarily the best choice in our
case because, from a managerial point of view, the
flattest solution is the one that most underestimates the

effort. We therefore considered a version of the
experiment having for goal function the inverse of
effort (1/e). The two problems are equivalent, except
that the flattest solution of one case corresponds to the
steepest one of the other, and vice-versa.
Moreover, when we considered features in the
logarithmic scale, we also compared the results
obtained by unprocessed effort and with its logarithm,
both in the direct and inverse versions. Differences

between the two could be connected to a better fit of
the function to be estimated. Note, for example, that
when a linearity test gives a negative outcome,
meaning that linearity regression cannot be linearly
applied, the logarithm is applied instead to raise the
probability that the data will fit a linear function

[23],[28].

**4. Validation Method and Evaluation**

**Criteria**

We assessed SVR’s effectiveness by randomly
splitting the dataset into a training (used to train the
algorithms) and a test set. Note that this was
completely distinct from the training set used to assess
the evaluation parameters. Such hold out methodology
assumes the experimental conditions to remain
constant, that is, that there is not a temporal evolution
which causes the experimental conditions to change. In
the final application, data collected in the past will be
used to build an estimator able to solve problems in the
future, and such procedure is effective only as long as
the overall contextual conditions remain sufficiently
constant. In such constant conditions, hold-out
validation is definitely fair, since the observations
included in the test set are completely different from
those used to obtain the estimates.

It is our view that considering only one split into
training and test sets, even if randomly selected, can be
misleading as it can correspond to either an extremely
advantageous or, on the contrary, disadvantageous,
split. Therefore, in our study, we used two random
splits, so that the probability of having such extreme
cases in both experiments was highly reduced. In order
to compare the results obtained using SVR with other
effort estimation techniques, such as Manual Stepwise
Regression (MSWR), Case-Based reasoning (CBR),
and Bayesian Networks (BNs), these two splits were
the same employed by Mendes in [20], where the
training set was obtained by randomly selecting 130
observations from the original 195 projects contained
in the Tukutuku database, while the remaining 65
observations were included in the test set.
To assess the accuracy of the obtained estimations, we
employed commonly used measures such as the *Mean*
*of Magnitude of Relative Error* (MMRE), *Median of*
*MRE* (MdMRE), and *Prediction at level 25* (Pred(25))

[8]. MRE is the basis for calculating MMRE and
MdMRE, and defined as:
MRE **=** |e-ê|/e (1)
where *e* represents actual effort and *ê* estimated effort.
MMRE and MdMRE represent the mean and the
median, respectively, of the MRE values of all the
observations in the test set. The difference between

MMRE and MdMRE is that the former is sensitive to
predictions containing extreme MRE values. Pred( *l* )
measures the percentage of estimates that are within *l* %
of the actual values, and *l* is usually set at 25.
Note that Kitchenham *et al.* [13] showed that
MMRE and Pred( *l* ) are respectively measures of the
spread and kurtosis of *z*, where ( *z* = ê|/e). They
suggested the use of boxplots of *z* and boxplots of the
residuals (e-ê) as useful alternatives to simple
summary measures since they can give a good
indication of the distribution of residuals and *z* and can
help explain summary statistics such as MMRE and
Pred( *l* ). Indeed, boxplots are widely employed in
exploratory data analysis since they provide a quick
visual representation to summarize the data, using five
values: median, upper and lower quartiles, minimum
and maximum values, and outliers [13].
The same authors suggested the use of the
Magnitude of Relative Error relative to the Estimate
(EMRE) as a comparative measure as well. The EMRE
has the same form as MRE, but the denominator is the
estimate, giving thus a stronger penalty to underestimates. As with the MRE, we can also calculate the
mean EMRE (MEMRE) and Median EMRE
(MdEMRE).
Following the suggestion of Mendes and
Kitchenham [14][21], we also compared MMRE,

978-1-4244-4841-8/09/$25.00 ©2009 IEEE


MdMRE, and Pred(25) using two models based on the
mean effort (i.e., MeanEffort) and median effort (i.e.,
MedianEffort) as predicted values, respectively. The
aim was to have a benchmark to assess whether the
estimates obtained with a prediction technique are
significantly better than estimates based on the mean or
median effort. In addition, as benchmark, we also
employed MSWR and CBR due to their frequent use in
Web & software effort estimation studies, and BNs, as
used in [22].
The statistical significance of the results was tested
using absolute residuals, to establish if one estimation
technique provided significantly better results than the
others [13],[28]. Statistical significance tests are used
to assess whether two sets of data come from the same
population. If they do, we can conclude that neither of
the two experiments significantly outperforms the
other.

Gaussian kernel were significantly smaller than those
obtained using C1, C2, C4, and C5 (p-values < 0.003).
Moreover, if we take into account summary measures,
the boxplots of absolute residuals, and the results of the
Wilcoxon test we can observe that C6 using the
Gaussian kernel also provided (not significantly) better
results than C3 with the Linear kernel.

**7. Conclusions**

In the paper, we described the application of
Support Vector Regression to a cross-company dataset
of Web applications, the Tukutuku database. In
particular, we explored and compared different
configurations and preprocessing filters to be applied
to data and tested them on two different splits of the
Tukutuku database into training and test sets. As a
result, we have observed that the flexibility of the
method, determined by the possibility of exploiting
different kernels and parameters settings, allowed the
learning mechanism to adapt to the characteristics of
the different datasets. In particular, on the former split,
SVR with linear kernel and log transformation of both
the features and the effort to be estimated
outperformed all other configurations and techniques
with a confidence of 95%. Also on the latter split the
log transformation of both features and effort obtained
very good results, but in this case using the inverse of
the log effort instead than directly the log effort proved
to be a better choice. Moreover, the Gaussian kernel
worked better than the linear one. All in all, in both
cases, SVR outperformed all other techniques, with the
exception of MSR on the second split, with a
confidence of 95%. The improvement on MSR on the
second split had a confidence of more than 90%.
In conclusion, we can affirm that SVR has proven
to be the best technique, among the ones we
considered, for predicting the development effort on
the considered cross-company dataset. Of course, the
experimental results here presented hold only with
respect to the Tukutuku database and they should be
assessed on further data as soon as they are available.
However, they are surely interesting enough to suggest
the use of SVR among the techniques that are suitable
for Web development effort estimation using a crosscompany database. As for future work, we intend to
identify the characteristics of the datasets that make
them more suitable for a specific kernel or parameter
setting with the aim to design a Recommender System
