**1.** **Introduction**

Software practitioners in general recognise the
importance of accurate estimates of development
effort to the successful management of major software
projects. Project attributes as size, duration and
complexity can also amplify the difficulties in finding
accurate estimates. Project managers and software
development organisations need accurate estimates at
early stages in a project life cycle to manage resources
properly.

Existing approaches to effort prediction fall into
three general categories [11]:

Expert judgement has been a widely practised
method through the years. However, the means of
deriving an estimate are not explicit and are not
therefore repeatable. Expert opinion, although always
difficult to quantify, can be an effective estimating
tool on its own or as an adjusting factor for
algorithmic models [7].

Algorithmic models have been the most popular in
the past, and attempt to represent the relationship
between effort and one or more project characteristics.
The main 'cost driver' used in such a model is usually
taken to be some notion of the software size (e.g. the
number of lines of source code, function points).
Although the precise formulation of each model
varies, at a higher level they may all be considered as
derivatives of [11, 12]:

Algorithmic models always need to be calibrated or
adjusted to local circumstances (this can be seen as
disadvantage of the approach). Examples of
algorithmic models are the COCOMO model [2], the
SLIM model [1O] and function points [1].

Estimation by analogy involves characterising the
project for which an estimate is required and using this
characterisation as a basis for finding similar or
analogous completed projects, for which effort is
known. These effort values are then used, possibly
with adjustment, to generate a predicted value of
effort. Finding the right analogies and assessing the
degree of similarity are the main difficulties of this
method.

**2.** **Estimation by Analogy**

The first step to se estimation by analogy is to
characterise the project for which the estimate is to be
made in terms of a number of variables (attributes).
These variables are then used to find other similar

projects (that have already been finished) and use the
values from their variables to estimate effort. In other

words, an estimate for the new project is made based
on the known effort values for the finished projects.

When applying estimation by analogy, there are a
number of questions that we need consider >11]:

- How can a project be described best? For web
applications, examples would be the type of
application domain, the number of documents
contained in a hyperdocument, the number or
links and the average of links per document. The
range of variables must be limited to the
information available at the point that the
prediction is required. The variables should
portray the project as precisely as possible. It is
also essential to choose at least one variable that

characterises the project in terms of its size. In
this case study, projects are the Web applications
developed or under development. Size variables
are the number of documents, the number of links,
the size (Mbytes) of the entire application.

- How are similarities between projects detected?
And, how much confidence is there in the
analogies? The number of analogies to search for,
i.e., the number of projects which best match the
new project, also needs to be identified.

- How can known effort values from the analogous
projects be used to derive an estimate for the new
project? Some options include using the mean of
the known effort values or the weighted mean of
known effort values. In the latter case higher
weights would be placed on closer analogies.

The estimation by analogy approach used does not
determine the number of variables that should be used

to characterise a project. Although in theory a greater
number of variables are better than a smaller number,
in practice the number of variables is determined by
the historical data available. Exceptions are when the
data collection is conducted with analogy in mind.


Here the number of variables can be previously
determined.

The analogies used in our work are calculated by
measuring the Euclidean distance in n - dimensional
space where each dimension corresponds to a variable.
Values are standardised so that each dimension

contributes equal weight to the process of finding
analogies >12].

Although the number of analogies used to estimate
the effort can vary from one to three, literature in the
field of software engineering suggest that one analogy,
followed by two analogies, are generally the most
effective options >12]. However, it is possible that
dissimilar datasets may reveal different characteristics.
It all depends on the number of finished projects to
choose from and how similar the projects in a dataset

are.

Once the analogous projects are identified, an
unweighted mean of the known effort values is used to
determine the predicted value.

3. The ANGEL Software Tool

Although it is possible to find analogies, using the
Euclidean distances, without the help of a computer
program, it can be time-consuming and error- prone as
the number of projects or variables increase.
Consequently, we have used an analogy effort
estimation tool that automates the process and
provides an environment where data can be stored,
analogies found and estimates generated. The tool
was developed at Bournemouth University under the
name of ANaloGy softwarE tooL (ANGEL) >11]. One
of the important features of ANGEL is the ability to
determine the optimum combination of variables for
finding analogies. This task can take a long time
depending on the number of variables as it employs a
brute force algorithm or exhaustive search of all
possible permutations. This is relatively slow for a
large number of variables [1] . Otherwise, ANGEL is
fully operational.

Figure 1 (see appendix A) shows part of a template
for recording project data. Templates are used to
describe the data that will be used in the estimation

process. They can be configured to match the specific
data collection environment of an organisation.

ANGEL does not impose any particular set of
variables to be used in the analysis, giving the user
freedom to define the best set of variables to

characterise a project. Consequently, the estimation
process can take optimal advantage of the data
available. The user chooses the number of variables

and their names. The only exceptions are the project
number, status and actual effort which are compulsory.
ANGEL uses the project number to uniquely identify
each project. The Status attribute shows whether or
not a project has been completed. Projects whose
status is "completed" can be used as a source of
analogy. The actual effort is mandatory for all
completed projects as it supplies the foundation for
prediction. Figure 2 (see Appendix A) shows the data
collected for one of the datasets used in this work.

Once the template has been created and the data has
been entered, the next step is to select the variables
that will be used to find analogies (see Figure 3 in
Appendix A). Not all the variables collected will be
useful for finding good analogies. The user can select
either all the variables described in the template or just
a subset of those.

Once the variables to use in the estimation have

been chosen, the next step is to run the estimation
algorithm so that the estimation can be produced. The
level of confidence that we have in using analogies
drawn from a given dataset is also provided as part of
the output (see Figure 4 in Appendix A).

Typically, where there are only a few projects or
where the projects differ very broadly in nature the
results will not be as accurate as for datasets

representing similar projects. The level of confidence
is calculated by finding the mean magnitude of relative
error (MMRE) and the Pred (25). They are computed
by means of jack knifing >11, 12] which involves
consecutively eliminating each project from the
dataset and using the remaining projects to derive an
estimate. The estimate is then compared with the
actual value and the absolute percentage error
computed. The mean of all absolute percentage errors
is known as MMRE >5], defined as:


The Pred(25) represents Predication at level n. It is
used as a performance measure to indicate the
percentage of projects a model predicts with a relative
error under the threshold n.

As Figure 4 shows (see Appendix A) the estimated
effort for a selected project, in this case Proj001, was
computed based on the completed projects from the
dataset. The predicted effort is of 58.83 hours. The
MMRE obtained was 43.71% and the Pred(25) was
52%. An MMRE figure below 50% indicates a good
model. The results for the Pred(25) means that the
prediction applies to 52% of the projects within 25%
of their actual effort.

The HEL group contains information about 29
projects and the LEL group information for 41
projects. The variables selected for the datasets used
were necessarily pre-determined since the data had
already been collected. However, the datasets had at
least four size-related variables: hyperdocument size,
connectivity, compactness and stratum.

In order to evaluate how precise the estimations
would be for each one of our datasets, the following
steps were followed:

- One project at a time had its status changed to
"active".



- ANGEL was used to estimate the best

combination of variables (using the "best
combination of variables" option) for 1, 2 and 3
analogies.

- Effort was estimated using 1, 2 and 3 analogies
and the corresponding "best combination of
variables".

- The MMRE was obtained using the actual effort
and the estimated effort closest to the actual

effort.

The MMRE for the LEL group was 52.23%.
Although this figure may indicate a usable model, we
decided to split the LEL group into two more

- The MMRE was 29.15%, indicating a usable

- The variables which contributed the most for the

For LEL-G2 our conclusions are as follows (see

- The MMRE was 28%, indicating a usable

- The variables which contributed the most for the

5. Conclusions and Future Work

Several comparisons can be drawn between the
process of estimation by analogy and the way humans
informally use analogies from the past to solve
problems in the present. Consequently one can assume
that the concepts supporting estimation by analogy are
easily understandable.

There are advantages and disadvantages associated
with using estimation by analogy methods [12]. The
advantages are as follows:
i) Estimation by analogy can succeed even where
no statistical relationships can be found [12].
ii) It is self-calibrating as opposed to algorithmic
models where calibration is essential.


iii) As it is a more intuitive method it is easier to
understand the reasoning behind a particular
prediction. Consequently the level of confidence
in a prediction can be enhanced or discarded if it
appears to be based upon flawed analysis.

The disadvantages are:
i) There are no answers concerning the effect of old
datapoints in the estimation as an organisation
develops and successively introduces new
technology. The question then arises: when
should such projects be removed from the
dataset?
ii) It is not clear why diverse sets of variables and
methods for generating the prediction are more or
less successful with different datasets. Clearly
there is a need for more investigation in this area.

In terms of further work, the two datasets used in
the work had four variables characterising in some
sense the applications. However, as size can be
described in terms of length, functionality and

complexity >6], further investigation is clearly
necessary to identify the best combination of variables
that give best results. We also want to investigate the
calibration of models to the environment in which they
are to be used, in the same way as the MERMAID
(Metrication and Resource Modelling Approach)
approach >8] adopts. The environments of interest are
any organisation involved in the development of Web
applications.

Another area of further work includes the

comparison between estimation by analogy and two
algorithmic models, namely linear regression and
stepwise multiple regression. Although literature in
software estimation has showed that the analogy
method outperforms or mirrors the best algorithmic
method >11, 12] we want to investigate whether or not
the results would be similar when applied to the
development of Web applications.

To conclude, there is an urgent need for adequate
Web development effort prediction at an early stage in
the development. As the use of the WWW (World
Wide Web) as a resource delivery environment
increases, effort estimation can contribute significantly
to the reduction of costs and time involved in

developing Web applications. In this paper we have
shown that analogy may be a viable estimation method
for prediction, particularly when given the necessary
tool support.

We do not, however, wish to create the impression
that analogy based prediction should replace
algorithmic methods. Dissimilar datasets will have
different characteristics implying that a variety of
techniques should be contemplated.
